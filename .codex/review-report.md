## 3. 明确建议

**通过。** 规格已达到可直接进入实现阶段的精度：每条功能需求都有唯一编号、可判定的验收标准与对应测试类型；技术选型与配置字段均锚定上游真实实现而非凭空设计；最高风险项已被识别并要求测试先行。

### 支持论据

1. **证据密度高**：73 条需求中涉及外部生态的字段名（`base_url`/`env_key`/`wire_api`/`agents.entries`/`<tool_call>`）全部来自 DeepWiki 对上游仓库的实际检索，非推测。
2. **歧义已消解**：用户表述中最大的不确定性（"codex hermes""deepseek hermes"是什么）在 §0 被显式澄清并给出可推翻的锚定说明。
3. **约束冲突已裁决且留痕**：AGENTS.md 的"删除安全设计"与技能模板的"必含 Security 章节"冲突被明确裁决，未被静默忽略。

### 关键发现

- 全平台唯一的高技术风险集中在 `StreamTagParser`：若采用整体正则匹配将在流式场景必然失效，因此 §8 阶段一明确要求该模块"先写测试后写实现"。
- `ProtocolAdapter` 抽象是让 DeepSeek 等非 Hermes 模型复用同一 agent loop 的关键，缺失它会导致 C2 与 C4 无法同时成立。

### 6.3 复审关键发现

- 最有价值的判断是**厂商数量与适配器数量解耦**：厂商由 2 家扩到 5 家，适配器仅从 3 个增至 4 个。若未查证线制而按"一厂商一适配器"直觉实现，会多出 2 个功能完全重复的模块。
- 本轮新识别的实现陷阱是**跨协议降级**：跨厂商 fallbacks 必然跨越协议边界，直接转发上一协议的请求体会产生格式错误。已新增 FR-LOOP-015 与 AC-020 覆盖，属需求层而非实现期才发现，风险已前移消解。
- 协议探测由「模型名正则」改为「提供商声明继承链」，使后续新增厂商无需改动探测代码，降低长期维护面。
